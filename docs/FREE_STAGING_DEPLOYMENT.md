# نشر نسخة التجارب المجانية

ملف `render-testing.yaml` يجهز واجهة ثابتة وخادم Node للتجارب على Render، مع قاعدة Supabase مستقلة. لا ينشئ قاعدة بيانات Render أو خطة مدفوعة، ولا يشغل ترحيلات على قاعدة المتجر الأصلية. النشر التلقائي متوقف.

## إعداد الخدمات

1. اربط حساب Render بالمستودع واختر ملف Blueprint: `render-testing.yaml` من فرع `launch/preparation`.
2. ضع عنوان قاعدة **التجارب فقط** في `SUPABASE_URL` ومفتاح الخادم الخاص بها في `SUPABASE_SECRET_KEY` داخل إعدادات الخادم الآمنة. لا تضع المفتاح في المحادثة أو GitHub أو متغير يبدأ بـ `VITE_`.
3. ضع عنوان واجهة التجارب الكامل في `PUBLIC_ORIGIN`، دون شرطة مائلة أخيرة. إذا لم يتحدد العنوان بعد، أكمل ضبطه بعد إنشاء الخدمات وأعد نشر الخادم.
4. ضع عنوان خادم التجارب الكامل في `VITE_API_URL`، دون شرطة مائلة أخيرة، ثم أعد بناء الواجهة. هذا المتغير يدخل في ملفات الواجهة وقت البناء.
5. احتفظ بـ `ADMIN_API_KEY` الذي يولده Render داخل إعدادات الخادم. يستخدمه المسؤول فقط؛ لا تضمّنه في ملفات الواجهة.

الدفع الإلكتروني متوقف، وقائمة مصادر البحث فارغة حتى اعتماد المصادر. لا تضف مفاتيح إرسال رسائل أو شحن حي أثناء التجارب. لا تضع `STORE_PUBLIC_URL` لنسخة التجارب؛ يبقى فهرس البحث العام غير مفعّل.

## التحقق قبل أي إطلاق

- فحص `/health` ثم فتح الواجهة من رابط Render.
- استخدام منتج تجريبي وتسجيل طلب دفع عند الاستلام من الواجهة إلى الخادم والقاعدة.
- التأكد من إجمالي الطلب، نقص المخزون، منع تكرار الطلب، سجل الإدارة، وإعادة المخزون مرة واحدة عند الإلغاء.
- اختبار الإدارة والطلب على الهاتف والكمبيوتر، ثم تعطيل المنتج التجريبي.
- عدم تشغيل عمال الإشعارات أو إرسال بيانات عملاء لموردين أثناء الاختبار.

ملف الإعداد ليس إثباتًا على نجاح النشر. يجب تنفيذ هذه الاختبارات على الخدمات المنشورة وتسجيل نتائجها قبل اعتماد النسخة.

## حدود الاستخدام

الخادم المجاني مناسب للتجارب: يتوقف بعد الخمول وقد يتأخر أول طلب عند الاستيقاظ. لا يعتمد عليه لإطلاق تجاري يقبل طلبات حقيقية. أي انتقال إلى خطة مدفوعة يحتاج مراجعة التكلفة قبل تفعيله. راجع حدود Render وSupabase الحالية في لوحة الحساب، ولا تربط قاعدة الإنتاج بهذا الملف.
