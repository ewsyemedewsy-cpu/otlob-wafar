# Emad Store V18 — نسخة تطوير مُراجعة قبل الإطلاق

هذه الحزمة تكمل العمل السابق، ولا تثبت تشغيل المتجر أو نجاح الحسابات الخارجية. الملفات القديمة محفوظة؛ النسخة المعدلة لم تُرفع إلى Supabase أو الاستضافة بعد.

## ما تغير

- سمة فاتحة وداكنة مع حفظ الاختيار، بحث، حفظ السلة، عرض المقارنة المتصلة، وتحسين العرض على الموبايل والكمبيوتر.
- إدارة الأصناف والصور والوصف والمواصفات والمخزون، مع حماية حد السعر وإخفاء بيانات المورد عن الواجهة العامة.
- تسعير عادي لا يقل عن 5% فوق تكلفة المورد مع احتياطي 0.5% مستقل. نصف الزيادة فوق 20% يحسن السعر؛ 20% ليست سقف الربح. الحالة الاستثنائية القديمة محفوظة في وظائفها المقيدة ولا تُفعل تلقائيًا في المسار العادي.
- مقارنة الأسعار الحديثة الموثقة فقط؛ الأسعار القديمة غير موثقة افتراضيًا حتى تُراجع مطابقة المنتج.
- إنشاء الطلب والمخزون ومنع التكرار داخل معاملة واحدة؛ استعادة الحجز مرة واحدة عند إلغاء طلب لم يُشحن.
- الحفاظ على سياسة التوصيل وموافقة العميل والفواتير ومراجعة المطالبات والطلبات السابقة؛ لا تُختلق موافقات للطلبات التاريخية.
- تصحيح إنشاء Paymob والتحقق من HMAC ومعاملة تحديث الدفع. الحفاظ على اسم paymob-webhook المستخدم سابقًا.
- إدراج الشحن في طابور واحد محمي، منع تراجع الحالة من إشعار أقدم، وحماية تشغيل عمال WhatsApp والشحن بأسرار منفصلة.
- الاحتفاظ بإشعارات المورد؛ كل مورد يحصل على أصنافه فقط. القالب المعتمد للمورد له خمسة متغيرات: رقم الطلب، المحتويات، اسم العميل، الهاتف، العنوان.
- تجهيز PWA، وتسجيل دخول العميل عند إعداد مفاتيح Supabase العامة، وفاتورة قابلة للطباعة بوصول محدود.

## نتائج الاختبار وحدودها

بناء Vite نجح. اختبارات HTTP والتسعير وPostgreSQL المحلي عبر PGlite نجحت؛ تشمل 10 آلاف حالة تسعير، ثبات البيانات القديمة، حد السعر بالقرش، عدم تكرار الطلب، المخزون، التكرار والإشعار الأقدم، رفض مبلغ دفع خاطئ، ومنع الوصول غير المصرح به. فحص Deno لثماني وظائف نجح. اختبارات متصفح Chromium على 1440 و390 بكسل نجحت للسمة والسلة والبحث والمقارنة وعدم امتداد الصفحة. فحص npm الكامل لم يظهر ثغرات معروفة وقت المراجعة.

هذه ليست اختبارات حسابات Paymob/Bosta/Meta الحقيقية، ولا اختبار ضغط إنتاج أو اختبار اختراق مستقل. صور المنتجات في المعاينة تجريبية؛ الصورة البديلة تُعرض عند تعذر تحميل الصورة.

## تشغيل محلي

يتطلب Node 24 وnpm. من جذر المشروع:

```bash
npm ci
npm test
npm run check:edge
npm run build:web
```

للمتجر: أعد ملفات البيئة من أمثلتها ثم شغّل `npm --prefix apps/web run dev`. للخادم: `npm run start:api`. متغيرات الواجهة العامة في `apps/web/.env.example`، وأسرار الخادم في `.env.production.example`، وأسرار Edge Functions في `supabase/.env.example`. لا تنشر الأسرار في كود الواجهة. متغير `PAYMOB_ONLINE_ENABLED` يبقى false حتى نجاح التجربة الكاملة.

## الترقيات

افحص مخطط المشروع الحالي أولًا، واختبر على نسخة staging من البيانات الحالية قبل التطبيق على الإنتاج. الملفات القديمة ليست بديلًا عن فحص المخطط الفعلي.

مسار قاعدة اختبار نظيفة/قديمة من V7 الذي اختُبر:

1. `db/schema.sql` **للتهيئة الأولى فقط**؛ لا تعِد تشغيله على قاعدة مهيأة.
2. `db/V12_compatible_upgrade.sql`
3. `db/V17_production_upgrade.sql`
4. `legacy-v17/V15_paymob_migration.sql`
5. `legacy-v17/V16_fulfillment_migration.sql`
6. `legacy-v17/V17_hardening_migration.sql`
7. `db/V14_admin_security_migration.sql`
8. `db/V18_compatibility_and_transactions.sql`
9. `db/V18_pricing_and_catalog.sql`
10. `db/V18_shipping_events.sql`

على مشروع موجود من V12–V17: افحص الأعمدة والوظائف والنسخ المطبقة ثم نفّذ الترقيات اللازمة فقط. لا تستبدل قاعدة البيانات الحالية. `V12_preserved_schema.sql` و`legacy-v17` مرجع لحفظ التاريخ؛ لا تنشر كود الوظائف القديم. الوظائف المعدلة المراد نشرها موجودة في `supabase/functions`.

يجب حفظ رابط callback السابق: `https://btjiifbaqjgcbpexkazz.supabase.co/functions/v1/paymob-webhook`. اضبط قائمة المديرين والسجلات وأسرار التشغيل والجداول الزمنية. `/admin.html` لوحة الطلبات السابقة وتستخدم جلسة Supabase لمدير معتمد. واجهة الأصناف داخل المتجر تستخدم خادم API المحمي.

## ما يمنع إعلان جاهزية الإطلاق

1. الاتصال بمشروع Supabase الفعلي ومراجعة مخططه ووظائفه وسجلاته، ثم اختبار الترقيات قبل التطبيق.
2. الاتصال بمستودع المصدر والاستضافة الحالية لدمج النسخة ونشرها على عنوان HTTPS الصحيح.
3. إعداد حسابات Paymob وBosta وWhatsApp وقوالب الرسائل ومناطق التوصيل الفعلية وجدولة العمال.
4. تجربة COD ثم الدفع الناجح والفاشل والتكرار والاسترداد والشحن والمرتجع وإشعارات العميل والمورد، باستخدام الحسابات التجريبية أولًا.
5. صفحة نتيجة الدفع والتحقق من الحالة بعد العودة تحتاج ربطًا نهائيًا بالعنوان المعتمد؛ العودة من البوابة وحدها ليست إثبات دفع.
6. البحث الآلي لدى المنافسين ومطابقة المواصفات بالكامل لم يُستكمل؛ عامل الأسعار السابق كان هيكلًا فارغًا. أُصلح التسعير وأضيف إدخال مقارنة موثقة، ويلزم مصدر بيانات/واجهة مسموح به لكل منافس وتجربة المطابقة قبل تشغيل الجمع الآلي.
7. مراجعة الشحن الذي انتهى بنتيجة غير مؤكدة قبل أي إعادة إرسال؛ المراجعة اليدوية تمنع تكرار شحنة عند انقطاع الاتصال بعد قبولها لدى المزود.
8. ضبط سياسات إلغاء الطلب غير المدفوع والمرتجعات واستعادة المخزون بعد فحص المنتج، واختبار تحميل وتشغيل وتثبيت PWA على الأجهزة المستهدفة.

لا توجد نسبة جاهزية أو موعد إطلاق مؤكد قبل هذه التجارب. النسخة السابقة محفوظة ولم تتغير حساباتك الفعلية أثناء هذه المراجعة.
